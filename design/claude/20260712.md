Good instincts on the three-table split (identity / intent / opinion). Here's where I'd push back or tighten things up.

The one structural fix I'd insist on: don't use md5 as the join key

Rotation is literally an action this app already supports, and in-place rotation of a JPEG changes its bytes → changes its MD5. The moment someone rotates a photo, every user_request and info row FK'd to the old md5 silently orphans from the photo it describes. Over months/years this will happen and you won't notice until you go looking for a comment that's "disappeared."

Fix: give newphotolib a real autoincrement id as primary key, keep md5 as a plain unique-indexed column on that row, and FK user_request/info to the id, not the hash. If a rotate/edit changes the md5, you update the md5 column on the existing row — history stays attached. This also lets you handle "same content, want to track as distinct entries" later if it ever comes up (it collapses fine by default via the unique index, but isn't structurally welded to the hash).

Your unresolved issue — bulk folder moves

I'd resolve this by not writing a user_request row for filesystem moves at all. Instead:
- newphotolib.path/name become a scanned/derived field: a reconcile job walks the surviving-copies tree, computes (or reuses a cached) MD5 per file, and upserts path/name by matching MD5. Ordinary mv, folder renames, batch reorganization done in Finder/terminal/a script just get picked up on the next scan — no per-photo bookkeeping required.
- user_request then only exists for actions initiated from inside the review app (the delete/rotate/mv buttons you click while reviewing) — which is exactly the pattern your existing actions table already uses for favorite/delete/rotate. Worth reusing that pattern/table rather than inventing a parallel one.

That cleanly separates "things I did externally in bulk" from "things I flagged one photo at a time while reviewing," and answers your "should this live outside the slideshow app" question: the bulk reorg can happen anywhere; the app's job is to reconcile, not to be the only path for moves.

Other gaps

- user_request: needs a target_path for mv requests (where to?), and separate executed_date from request_date so you can tell "I asked for this" from "this actually happened." Also status should probably allow failed (destination existed, source missing), not just rejected/completed/pending.
- info as append-only: reasonable if intentional (never lose a past comment/rank), but confirm that's the intent — "current" rank then means MAX(entry_date) per md5/id, which is a bit more query work everywhere you read it. If you don't actually need history-of-opinion, a single mutable row per photo is simpler; you can always add an audit log later if you find you want one.
- category: free text will drift over years ("vacation" vs "Vacation" vs "trip"). For a single-user app I wouldn't build a controlled-vocabulary table — just have the UI autocomplete against SELECT DISTINCT category, cheap and keeps flexibility.
- Add created_at/updated_at on newphotolib — lets the reconcile scan skip unchanged files by mtime instead of re-hashing everything every time, which matters once this is thousands of photos over years.

On "secure so I don't have to do this again"

I read that as durability, not access-control — the risk is data loss/corruption over a long-lived process, not an attacker. Concretely:
- Never let the app rm/overwrite anything under ../fotos/ (originals) — only ever operate on the surviving-copies tree, exactly as you planned.
- Don't wire delete requests to auto-execute. Keep user_request(status=pending) as a queue, and require a separate, explicit "commit" step (even just a terminal command you run) to actually delete — so a stray click in the review UI can't nuke files.
- Back up fotos.db before any reconcile/batch run — it's cheap and it's where months of ranking/comment work lives.
- New tables/queries should follow the existing db.ts pattern: parameterized db.prepare(...).run(?), and reuse validateWhereClause-style guarding for anything that takes user-supplied SQL fragments.
